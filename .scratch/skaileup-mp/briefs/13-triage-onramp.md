## 1. mp's `triage` skill — what it actually is

`~/.agents/skills/triage/`. **429 lines across four files:**

| file | lines | role |
|---|---|---|
| `SKILL.md` | 112 | the state machine + procedure |
| `AGENT-BRIEF.md` | 207 | how to write a durable agent brief (the output artifact) |
| `OUT-OF-SCOPE.md` | 105 | the `.out-of-scope/` KB (ticket 05 closed this half) |
| `agents/openai.yaml` | 5 | `allow_implicit_invocation: false` |

**Frontmatter carries `disable-model-invocation: true`.** It is a slash-command skill only —
the model never reaches for it; a human types `/triage`.

**Input.** An *issue tracker*. Not a repo, not a file: `gh`-shaped issues and external PRs,
addressed by number (`#42`). "A PR is an issue with attached code," same roles, same states.
The tracker identity and the label vocabulary must have been *configured* — the skill says
so twice, and points at `/setup-matt-pocock-skills` when they are missing.

**What it produces.** Labels + comments *on the tracker*, in four terminal shapes:

- `ready-for-agent` → an **agent brief comment** (`AGENT-BRIEF.md`'s template: category,
  summary, current/desired behavior, key interfaces, acceptance criteria, out-of-scope).
- `ready-for-human` → same structure plus why it can't be delegated.
- `needs-info` → a triage-notes comment (established-so-far + specific questions to @reporter).
- `wontfix` → close, and *if* a rejected enhancement, a `.out-of-scope/<concept>.md` file.

Every comment must open with `> *This was generated by AI during triage.*`

**The state machine.** 2 category roles (`bug`, `enhancement`) × 5 state roles
(`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), with an
invariant — exactly one of each, conflicts get flagged to the maintainer — and declared
transitions (`needs-info` returns to `needs-triage` once the reporter replies).

**Its five steps, and where the judgment lives.**

1. **Gather context** — read the issue/PR whole, parse prior triage notes, explore the
   codebase *via the project's domain glossary*, respect ADRs; run **two checks**:
   (a) redundancy — is this already implemented, searched *by domain concept, not wording*;
   (b) prior rejection — read `.out-of-scope/*.md` and surface a concept-similarity match.
2. **Recommend** category + state with reasoning, then **wait for direction**.
3. **Verify the claim** — reproduce the bug / run the PR's tests *before any interview*.
   "A confirmed verification makes a much stronger agent brief."
4. **Grill (if needed)** — calls the Skill tool twice, for `grilling` **and**
   `domain-modeling`, sharpening domain terms and updating `CONTEXT.md`/ADRs inline.
5. **Apply the outcome** (the four shapes above).

Plus a **quick state override** path ("move #42 to ready-for-agent" → trust, apply, skip
grilling) and a **resume** path (read prior notes, don't re-ask resolved questions).

**Dependencies on other mp skills.**

| dependency | absorbed by skaileup? |
|---|---|
| `grilling` (step 4) | **Yes** — map premise 6 absorbs it; ticket 07 makes it *a global install called by name*, which is exactly how `triage` uses it |
| `domain-modeling` (step 4) | **Already absorbed** — ticket 02: `contracts/domain_model.md` is a faithful port |
| `setup-matt-pocock-skills` (tracker + label config) | **No.** Ticket 02 verdict was ABSORB *(pattern only)* — the explore→present→confirm→write shape, into `scope-project`. The *config file it writes* has no skaileup equivalent |
| `.out-of-scope/` (`OUT-OF-SCOPE.md`) | **No** — closed by ticket 05 |
| `AGENT-BRIEF.md` | **Not as a file.** Ticket 02 flagged its durability rule ("don't reference file paths, they go stale") as worth absorbing *broadly*, not as part of triage |
| `to-spec` / `to-tickets` | **Not dependencies.** They are the *opposite* on-ramp — see §6 |

**The structural claim that separates the two on-ramps** lives in `ask-matt/SKILL.md:38-40`,
not in `triage` itself:

> Bugs and requests piling up → `/triage`. It moves issues through triage roles and produces
> agent-ready issues, which `/implement` later picks up. **Triage is only for issues you
> didn't create**: bug reports, incoming feature requests, anything that arrives raw.
> Tickets that `/to-tickets` produced are already agent-ready, so **don't triage them**.

**What it assumes about its repo:** a configured issue tracker with those five labels; a
maintainer in the loop at step 2 and step 4; a runnable test/repro loop (step 3); a domain
glossary + ADRs to read against (step 1); `.out-of-scope/` on disk. **Four of five of those
are host/process assumptions, not `_concept/` assumptions.**

## 2. `mockup-feedback-triage` — how much is routing, how much is feedback

Files: `SKILL.md` **98 lines**, `triage.py` **106**, `validator.py` **107**, plus
`tests/expected/` fixtures and two session fixtures in `_test-fixtures/sessions/`.

**Input.** `_concept/_feedback/sessions/<sid>.json`, written by `mockup-feedback-annotate`
from an in-browser overlay. Per `schemas/session.schema.json` an annotation is
`{id, sessionId, createdAt, specRef{element, screen?, feature?, journey?, route?, provisional?},
body, category ∈ {change,add,remove,question}, status ∈ {open,applied,dismissed}}`.

**Output.** `_concept/_feedback/triage/<sid>.json` =
`{sessionId, triagedAt, groups:[{file, annotations:[id]}], unresolved:[{annotationId, reason}]}`.

**Deterministic — ticket 06 is right.** No LLM anywhere. The skill body is three steps:
find unprocessed sessions, shell out to `triage.py`, print a report. Ticket 06 already ruled
it "was never a skill (98 lines wrapping a deterministic `triage.py`)" and folded it into
`mockup-feedback` alongside patch and apply.

**The entire routing logic is one function, ~12 lines** (`triage.py:22-38`):

```python
for key, subdir in [("screen","experience/screens"),
                    ("feature","experience/features"),
                    ("journey","experience/journeys")]:
    val = spec_ref.get(key)
    if val:
        rel = f"{subdir}/{val}.md"
        return (rel, None) if (concept_root/rel).is_file() else (None, f"file not found: _concept/{rel}")
return None, "no specRef target (screen/feature/journey all absent or null)"
```

**General vs feedback-specific — the honest split:**

*General (would survive into any router):*
- The three-way `screen > feature > journey` priority order.
- The `<subdir>/<value>.md` path convention against `_concept/experience/`.
- The existence check, and the discipline that unresolved items are **recorded, not dropped**
  ("The script exits 0 even if some annotations are unresolved").
- Grouping N inputs by target file, so the next step opens each file once.

*Feedback-specific (does not survive):*
- The `specRef.element` anchor — meaningless without an annotated walkthrough DOM.
- `sessionId` / session-file discovery / "unprocessed = no `triage/<sid>.json` yet".
- `provisional`, `route`, `status` — read by `patch`/`apply`, not by a router.
- `category` (`change|add|remove|question`) is **not read by `triage.py` at all**. It is
  `patch`'s dispatch key (LLM for `change`, templated for the other three).

**The decisive asymmetry, and it is not about size.** `mockup-feedback-triage` never
*decides* anything. The annotator already supplied the target (`specRef.screen: "01_user_auth/login"`);
the script only **dereferences a supplied reference into a path**. mp's `triage` has no
supplied target — it *classifies* (category), *assigns state*, *verifies*, *grills*, and
*writes a brief*. On the axis that matters — who chooses the destination — the two share
nothing. What they share is a *name*.

Scope of its target space: **3 subdirectories**, all under `_concept/experience/`. It cannot
route to `discovery/`, `blueprint/`, `_meta/`, `dossiers/`, or a decision record.

Durability note: `_concept/_feedback/sessions/` and `index.json` are **gitignored**
(`mockup-feedback-annotate` SKILL.md:33-36, 117-118). The feedback queue is ephemeral by
design; a triage queue that survives a re-clone would be a different storage decision.

### Near-misses, and exactly why each does or doesn't count

**`ops-add-feature` (316 lines) — the closest thing, and it is close.**
- *For:* Its trigger list is literally intake language: "add a feature", "modify the login
  feature", "change the requirements for X". Its required input is
  `feature_description: "What feature do you want to add or change?"` plus
  `feature_mode ∈ {new, modification}`. It cascades through journeys / techstack /
  architecture / datamodel / screens and "optionally triggers implementation."
- *Against:* (a) **It is in zero flows** — `grep 'skill: ops-add-feature' flows/` returns
  nothing; it is reachable only conversationally, named once in the orchestrator's
  "When NOT to use" list (`skaileup/SKILL.md:66`). (b) It **hard-gates** on
  `_concept/discovery/brief.md` and a non-empty `_concept/experience/features/`. (c) It
  **assumes the request is already a feature.** It has no classify step, no
  bug/enhancement distinction, no "is this already implemented", no "was this already
  rejected", no reject path at all. It is a *cascading writer*, not a router: the routing
  decision ("this is a new feature") was made by the human before invoking it.

**`ops-reverse-engineer` (621 lines) — the only genuine "work the collection didn't create"
entry, at the wrong granularity.** It is a flow entry node (`skaileup-concept-reverse`) and a
`shape` option in `scope-project`. But its unit is *an entire repository* → bootstrap a whole
`_concept/`. It is a one-time bootstrap, not a per-request intake; running it twice is not
what a second bug report wants.

**The `mockup-feedback` cluster — an on-ramp, but mid-flow and narrow.** The `mockup-feedback`
sub-flow is referenced by exactly two flows (`appbuilder-standard`, `appbuilder-complex`), and
only *after* a walkthrough exists. It is real intake — external humans, work the collection
didn't create — but it is (a) reachable only inside a pipeline run, (b) restricted to
annotations on rendered elements, (c) routed by a reference the annotator supplied, and
(d) gitignored/ephemeral.

**The other `ops-*` skills — all inspection, none intake.** `ops-review` (audit/garden
`_concept/`), `ops-sync` (fix cross-references), `ops-trace` (traceability matrix),
`ops-eval-{concept,feature,product}` (adversarial gates). Each *reads* existing artifacts and
reports or repairs; none accepts an external request as input. The `ops-project-*` suite
(overview / subsystem-map / integration / review) is **out of scope per the map** anyway.

**`skaileup-stepwise`** starts at `scope` like the rest; "stepwise" is about pacing, not entry.

**Conclusion available to the grill:** the gap is **real** — no per-request entry point for
work the collection didn't create, and no vocabulary for one — but the ticket's phrasing
overstates it twice: the entry is `scope`, not a brief, and `ops-add-feature` is a genuine
partial on-ramp for the "enhancement" half, just an unrouted and ungated-the-wrong-way one.

## 5. Domain placement and naming — collision mechanics

**Ticket 04's line:** `quality` checks `src/`, `ops` checks `_concept/`. A triage skill that
resolves an incoming request against `_concept/` sits in **`ops`** on that rule; `ops-triage`
is a legal 2-segment name. (Counter-pressure worth naming: if triage's step-3 *verify* means
reproducing a bug against `src/`, the artifact under inspection is not purely `_concept/`.)

**The bare-name collision is real and verified.** Ticket 04's argument was "a bare `research`
installs to `.claude/skills/research/`, the same path as the global mattpocock install, and
the two clobber each other." Mechanics confirmed:

- `workspaces/packages/workspaces/core/src/driver-targets.ts:56,63` —
  `claude-code.local.skill = ".claude/skills"`, `claude-code.global.skill = "~/.claude/skills"`.
  Also `core/src/framework.ts:30`.
- `~/.claude/skills/triage → ../../.agents/skills/triage` — **the mp `triage` is installed
  globally at exactly that leaf name today** (one of ~25 such symlinks).
- Precise mechanic: a `-mp` skill named `triage` installs to project-local
  `.claude/skills/triage/`, which **shadows** the user-level `~/.claude/skills/triage`. Not a
  filesystem overwrite — a precedence shadow — but the effect is the same: in any project that
  installs `-mp`, mp's `/triage` becomes unreachable. Same class of breakage as `research`.
- Ticket 04's rule stands unqualified: **all absorbed mp skills take a domain prefix, no
  exceptions.** Under that rule the name is `ops-triage` (or `ops-<something>`), never `triage`.

**Also from ticket 01/04, relevant to any new skill:** `name:` is the whole identity —
install path, flow `data.skill`, and grounding input path
`_concept/_grounding/<name>/input.json`. Under ticket 04 the directory must equal `name:`
character for character. Under ticket 15, any flow node for it must declare
`data.phase ∈ {conceptualization, implementation, review}`.

## Open tensions

1. **Does a router earn a skill when its target set is 8 known skills and 3 unresolved
   tickets?** `spec-feature`/`build-plan`/`build-implement`/`build-branch` plus the four
   mockup skills exist on paper; tickets 08, 17 and 18 are still open and 10 is blocked. A
   router specified now routes into a set that will change, and the map's own discipline is
   "decision tickets first — don't port ahead of the shape." Against that: this ticket exists
   to close the question *either way*, and refusing costs one line on **Out of scope**.

2. **The one-decision problem.** After ticket 07 collapsed the concept side to a single entry
   (`spec-feature`) and the build side to `build-plan`, the routing decision reduces to
   roughly: *is this a new feature (→ `spec-feature`), a defect against built code
   (→ `build-plan`/`build-implement`), a mockup annotation (→ `mockup-feedback`), or a
   refusal (→ a decision record)?* Ticket 07 used exactly this reasoning to delete tier-based
   routing: "with one entry skill per side there is nothing left to route to." Does that
   argument apply to this router too, or is the classification *itself* the value — with the
   route falling out as a by-product?

3. **The verify step is the part with no home.** mp's step 3 — reproduce the bug / run the
   PR's tests *before* grilling — is the step that makes the brief strong, and it inspects
   `src/`, not `_concept/`. Ticket 04's `quality`/`ops` line puts anything inspecting
   `_concept/` in `ops`. Does an `ops-triage` that reproduces bugs violate the line, does the
   verify step get dropped (leaving a skill that only classifies), or does the line need a
   third answer for a skill that reads both sides?

4. **Which tracker, and is there one?** mp's triage is `gh`-shaped and *requires* a configured
   tracker + label vocabulary that `setup-matt-pocock-skills` writes — a setup step ticket 02
   confirmed skaileup does not have and only absorbed *as a pattern*. skaileup's own repo has
   1 closed issue; `platform` has 500 and already runs mp's labels directly on GitHub.
   forge-concept has a *document comment* API instead. So: does `-mp`'s triage read GitHub
   (duplicating what mp already does for platform), read forge-concept's comment store
   (which no skill reads today), read a file in `_concept/`, or take a request straight from
   the conversation with no tracker at all?

5. **Is the queue actually skaileup's queue?** The 500-issue, 43-`user-feedback` backlog is on
   `platform` and `workspaces` — repos that *have* `_concept/` but are not driven by the
   skaileup pipeline, and whose triage already runs on mp's skills. If the incoming work never
   arrives at a skaileup-built app, an `ops-triage` has an empty inbox and a duplicate
   upstream. If it does, the question is why `-mp` should re-implement a skill the human
   already has installed globally.

6. **Absorb, or just call it by name?** Map premise 6 splits mp's skills two ways: pipeline-
   shaping ideas get absorbed with a skaileup prefix; domain-neutral ones (`tdd`,
   `code-review`, `prototype`) stay global installs called by name — the mechanism ticket 07
   used to collapse four grill-shaped skills to zero. mp's `triage` is *mostly* domain-neutral
   (a tracker state machine) with one `_concept/`-flavoured seam (route the accepted item into
   the right skaileup entry). Is the right answer a skill at all, or a one-paragraph rule in
   the orchestrator that says "for work you didn't create, call the global `triage`, then
   enter at `spec-feature`"?

7. **Does `mockup-feedback-triage` collapse into a general triage — and can it?** Ticket 06
   already ruled it "was never a skill" and folded it into `mockup-feedback`. Its routing is
   ~12 lines of *dereference* over 3 subdirectories, with the target supplied by the
   annotator; a general triage *chooses* the target. If they merge, the deterministic
   `triage.py` becomes a script inside a judgment skill — which is exactly the shape ticket 06
   said was wrong. If they don't merge, `-mp` ships two things called triage that share a name
   and nothing else — the naming problem ticket 05 exists to prevent.

8. **If it is refused, what does the map say?** The ticket asks for **Out of scope**, not fog.
   Refusal has a shape too: does the collection then state positively that its entry is
   `scope-project` for new work and `ops-add-feature`-or-successor for changes to a live
   concept — and does *that* force ticket 08 or a new `ops` ticket to rule on
   `ops-add-feature`, which today is owned by no ticket and referenced by no flow?

#### 1. mp's `triage` — what it is

- **Human-only.** `SKILL.md:4` `disable-model-invocation: true`; `agents/openai.yaml` sets
  `allow_implicit_invocation: false`. A maintainer types `/triage` (`:49`).
- **Its host is an issue tracker, not a repo.** Issues and external PRs by number (`:11`); labels come

  (`:58-64`). Machine: 2 category × 5 state roles, one of each, declared transitions (`:26-45`).
- **Five steps** (`:70-86`): gather context — two checks, redundancy *by domain concept* and prior
  rejection via `.out-of-scope/*.md` → recommend and **wait** → verify by reproducing the bug /
  running the PR's tests → grill (calls `grilling` **and** `domain-modeling` by name, `:76`) → apply
  one of four outcomes. It **writes** labels and tracker comments, each opening with a mandated AI
  disclaimer (`:13-17`); the only *file* it writes is `.out-of-scope/<concept>.md` (`:85`).
- **Assumes** a configured tracker + labels, a maintainer present at steps 2 and 4, a runnable repro

### What the glossary already committed to

`CONTEXT.md:97-102`, verbatim: a decision record is "an append-only note of a choice that was **hard
to reverse**, **surprising without context**, and a **real trade-off**. All three, or it is not one.
**A rejected scope decision is a decision record marked rejected, not a separate store.** Recorded at
the level it binds: the collection, the design, or the build." `_Avoid_: ADR log, rationale,
out-of-scope file`.

A vocabulary ruling with **no implementation behind it in `-mp`**: no `rejected` status in the format
contract, no skill that writes a decision record, no path reconciled to ADR 0007, and no reader that
dedups against one the way `OUT-OF-SCOPE.md:74-76` does. The ticket's "Note from ticket 05" closes
the second half on the strength of this paragraph alone.
