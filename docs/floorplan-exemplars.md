# Floorplan exemplars

Where each floorplan in `rulebook/floorplans/` was seen in real code. A maintainer's aid; it is not part of the shipped `app-design-rulebook` asset, and no skill reads it.

**Using it.** Paths are relative to `~/devBench/` and written as plain inline code, because the projects sit outside this repo. To add a floorplan, find the nearest reference here (or in the image-tool families below), open the file, and copy the geometry — regions, what folds at 640 px, what becomes an overlay — not the styling. Then write the floorplan's `README.md` and `preview.html` per `rulebook/README.md § Adding or retiring`, and add its row to the table. A row marked **no strong exemplar** was derived from rules and from adjacent references; say so in the floorplan's README rather than implying field proof.

## Cross-project conventions behind the constraints

Seen in code, not only in rulebooks: drawers hold secondary or admin content and modals hold short forms and confirmations; `?neu=<kind>`, `?node=` and `?view=&tags=` deep links; one shared confirmation dialog with a busy state; an undo toast; sidebar and column widths persisted per browser; shortcuts suppressed while a dialog is open or an input has focus; four views over one dataset through tabs. A floorplan's interaction constraints should stay consistent with them.
