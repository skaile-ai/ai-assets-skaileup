# _concept/10_blueprint/datamodel/

The project's data model, derived from the journeys and the glossary and written three ways: `model.dbml` to read, `model.json` for the editor canvas, `seed.json` for everything that needs realistic data. It runs before any feature exists, so it is the vocabulary that feature specs, behaviors and screens are written against: downstream skills read entity names from `model.json` and never coin their own, and each feature spec lists the models it uses in its own `data_entities[]` (the model holds no list of features). The model is stack-neutral — types are semantic, never SQL or Prisma — because translating it here would freeze a schema before the stack's migration tool has seen it. Node files: `tree/10_blueprint/datamodel/model.md` and `tree/10_blueprint/datamodel/seed.md`.

## Format

`architecture-datamodel` owns `model.dbml`, `model.json` and `seed.json`. A stack-specific schema file is `build-database`'s alone: a translation of `model.json` for one migration tool, written where the chosen template's `## Migration / ORM` section says, and the canonical files are never edited to match it.

## Naming

Names are settled against `_concept/glossary.md` before modelling: where the glossary has a term the model uses it, and a word on a term's `_Avoid_` list is renamed to the term. Output conventions (PascalCase model names, camelCase fields in Prisma or PostXL) are applied by the stack translator, never in the semantic layer.

**Entities**
- Names are `lowercase_snake_case` singular (`user`, `task`, `project_member`); no two entities share a name.
- Every entity declares `standard_fields` including at least `["id", "created_at", "updated_at"]`; `id` is `uuid` with `primary: true`, the timestamps are `datetime`.

**Fields**
- Names are `lowercase_snake_case` (`display_name`, `assigned_to_id`).
- The type is a semantic type (`tree/10_blueprint/datamodel/model.md`), never a backend type.
- An optional field uses `required: false`, never a `?` suffix.

**Enums**
- Values are PascalCase (`Draft`, `InProgress`, `Done`).
- Inline enums use object format, `{"Draft": "description", "InProgress": "description"}`, and auto-name as `{entity_name}_{field_name}` (`task_status`, `user_role`).
- Every named enum is referenced by at least one field; standalone enum ids are `lowercase_snake_case` and match their purpose.

**Relations**
- A many-to-one field name ends in `_id` (`owner_id`, `project_id`) and its type is the referenced entity name in snake_case.
- Inverse relations are generated by the translator and never declared.
- A many-to-many relation has an explicit junction entity.

**Seed data**
- Entity keys are the singular snake_case entity names in `model.json`, field names match the model, enum values are PascalCase, relation fields end in `_id`.

## Writing it

1. **Read what the model is built from.** `_concept/04_journeys/stories.yaml` is the main source: actors, stages and EARS criteria — event criteria become transitions, state criteria become guards, and what a journey creates, changes or looks up is an entity or a field. Project types that grow no journeys (`api-service`, `cli-tool`, `data-pipeline`, `library`) have no such file; the model then comes from the brief's hero flow and problem plus the glossary's terms, and the questions in step 3 carry what the journeys would have. `_concept/brief.md` gives the domain and `_concept/glossary.md` (always required) the words already pinned.
   - `_concept/10_blueprint/techstack.md`, when it exists, gives translation hints only (a stack that forces a join table); without it the model stays generic.
   - `_concept/10_blueprint/architecture.md`, when it exists, usually implies entities for a custom module or integration; without it, an entity only an integration needs surfaces later and this step re-runs.
2. **Settle the vocabulary before modelling.** List every candidate entity and enum vocabulary the journeys (or the brief) imply — each journey's `candidate_entities` is the starting list — plus entities with no journey behind them (sessions, audit logs, job records), and check each against the glossary per `## Naming`. A concept with no term is not appended to the glossary here: name it and hand back, and the flow re-enters `concept-glossary`, which pins it before this step goes on.
3. **Ask what the journeys left ambiguous** (one question per message — `tree/README.md § How a skill runs`): what each journey stores, how things connect ("a user has many tasks"), which roles may see or change what. The roles answer feeds the seed's `permissions` scenario and the fields those rules evaluate on. The grants themselves are the feature specs' `## Permissions` tables; this step runs before them, records no grants, and on a re-run reads those tables where they exist and seeds the roles and grants as written there.
4. **Approve in plain language** — what the app keeps track of and how those things relate, in the user's words, counts underneath. Write nothing before the user says yes; a model features, screens and seeds are about to name is cheapest to change while it is still a paragraph.
5. **Write `model.dbml` and `model.json`** per `tree/10_blueprint/datamodel/model.md`, applying `## Naming`. An `m2m` gets an explicit junction model; a raw SQL type here survives into a migration that will not apply.
6. **Write `seed.json`** per `tree/10_blueprint/datamodel/seed.md`, with all four standard scenarios plus `permissions` when the journeys name distinct roles.
7. **Hand a stack export to `build-database`.** When the user asks for a stack-specific schema, `build-database` writes it against these files rather than replacing them.

## Materialising the database

`build-database` turns the canonical model into the stack's schema, then the seeds into runnable scripts. Which stack-specific file results depends on the stack in `techstack.md`:

| stack signal | stack-specific file |
|---|---|
| generic / unknown | none — `model.dbml` + `model.json` are the schema |
| Prisma | `schema.prisma` |
| PostXL / NestJS | `postxl-schema.json` |

The file lives where the chosen template's `## Migration / ORM` section says; its `## Seed` section gives the seed layout and run command, selected by the `seed_format` atom (`prisma`, `drizzle` or `sql`).

**Semantic type translation**

| Semantic | Prisma / PostXL | Supabase | Raw SQL | Directus |
|---|---|---|---|---|
| `string` | `String` | `text` | `VARCHAR(255)` | `string` |
| `text` | `String` | `text` | `TEXT` | `text` |
| `richtext` | `String` | `text` | `TEXT` | `text` (WYSIWYG) |
| `integer` | `Int` | `int4` | `INTEGER` | `integer` |
| `float` | `Float` | `float8` | `DOUBLE PRECISION` | `float` |
| `decimal` | `Decimal` | `numeric` | `NUMERIC` | `float` |
| `boolean` | `Boolean` | `bool` | `BOOLEAN` | `boolean` |
| `date` | `DateTime` | `date` | `DATE` | `date` |
| `datetime` | `DateTime` | `timestamptz` | `TIMESTAMPTZ` | `timestamp` |
| `enum` | `enum` | `text` + CHECK | `VARCHAR` + CHECK | `string` (dropdown) |
| `json` | `Json` | `jsonb` | `JSONB` | `json` |
| `uuid` | `String @id @default(uuid())` | `uuid` | `UUID` | `uuid` |
| `password` | `String` | `text` | `TEXT` | `hash` |
| `slug` / `string` unique | `String` + `@unique` | `text` | `VARCHAR(255)` | `string` |
| `email` / `string` | `String` | `text` | `VARCHAR(255)` | `string` |
| `url` / `string` | `String` | `text` | `TEXT` | `string` |
| `image` | `String` (URL) or `imageId → File` | storage ref | `TEXT` | M2O → directus_files |
| `file` | `String` (URL) or `fileId → File` | storage ref | `TEXT` | M2O → directus_files |
| optional (`required: false`) | `Type?` suffix | `NULL` | nullable column | — |
| `m2o` | field ending `Id`, type = model name | FK | FOREIGN KEY | M2O |
| `o2m` | auto-generated inverse | — | — | O2M |
| `m2m` | explicit junction model | junction table | junction table | M2M |

**Conventions the model deliberately leaves out**
- `standard_fields` expands to an auto-generating UUID primary key plus `created_at`, and `updated_at` wherever the model declares it.
- Columns are snake_case.
- `on_delete` comes from the relationship in `model.json` and defaults to SET NULL where unset, which orphans a row rather than deleting one nobody asked to delete.
- Every `m2m` gets a junction table with the two foreign keys; `o2m` is generated from its `m2o`, never written by hand.

**Schema validation** — six checks before migrating: every entity in `model.json` has a table; every relationship is a foreign key or a junction table; every enum is defined; no semantic type survives in the output; primary keys auto-generate; on-delete behaviour matches `model.json`.

## Checks

- `model.dbml`, `model.json` and `seed.json` exist, the model is approved, and every model name and enum vocabulary is a term in `glossary.md`.
- `seed.json` carries all four standard scenarios.
- The mechanical rules in `## Naming` hold; a violation is a finding in the audit report.
