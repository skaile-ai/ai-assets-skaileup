# Ownership

## Ownership

Read anything, in any order; write only the artifacts you own, through the owner node's contract. `02_grounding/` is readable by every skill. To an artifact another skill owns you add nothing in place: you propose entries for it in a proposal file of your own, and only when you are listed under that node's `may_propose`. A project file outside `_concept/` other than `APP-DESIGN.md` and `docs/adr/` (a `GLOSSARY.md`, docs) is a source to read and cite, and stays the project's own: a term or decision it lacks is proposed to the artifact that owns that kind of entry — a decision to `docs/adr/` (`tree/docs/adr/README.md`). The one exception is the project glossary, the file that holds the words when the project keeps its own: a proposed word is still a proposed entry with `target: _concept/glossary.md` in either mode, and on promotion `concept-glossary` writes its definition and `_Avoid_` line into the project glossary. There it writes only the definitions of terms it adds, moves or promotes, keeping every entry written by `domain-modeling` or by hand as it stands (`tree/glossary.md § Where the words live`). `06_behaviors/` and `10_blueprint/architecture.md` are optional; a reader checks for existence before reading.

A node's frontmatter carries two keys, both required:

```yaml
owner: [concept-glossary]   # skills whose `produces` resolve here; [] when nothing generates it
may_propose: []             # skills that may target this artifact in a proposal file; disjoint from owner
```

A directory node lists the owners of the parts it covers. `may_propose` names skills of this collection and repeats no owner.

**Proposed entry.** One addition a non-owner offers to an artifact, written as an entry of its own proposal file `_concept/proposals/<proposed_on>-<proposed_by>-<scope>.yaml`, never into the artifact (format and steps: `tree/proposals/README.md`). Each run that proposes anything writes one new file and edits no other run's file, so parallel runs never write the same path. An entry names its `target` (the project-relative path of the owner's artifact), its `anchor` (where it lands, in the grammar the target node defines), its `payload` (the entry in the target node's own format), its `source` (an evidence reference or the user's words) and `status: proposed`. The proposer must be listed in the target node's `may_propose`; a glossary entry targets `_concept/glossary.md` (a `GLOSSARY.md` or legacy `CONTEXT.md` target resolves to `tree/glossary.md` as well), `APP-DESIGN.md` resolves to `tree/APP-DESIGN.md`, a decision record targets `docs/adr/` (`tree/docs/adr/README.md`). It adds and never edits a confirmed entry. When the target artifact does not exist yet, the proposer creates nothing there; the owner's first run creates it. The owner of the target settles each entry with the user, unless the target node's `## Format` names an approval that already covers it, and that is its one write into a file it did not create: it promotes the entry by writing `payload` into its artifact at `anchor`, in the artifact's own format and with no marker, or rejects it with a `reason`; either way it sets `status`, `settled_by` and `settled_on` in the proposal file, which stays as history. A rejection needs no decision record. The owner's artifact never holds a proposal or a proposal marker. A pending entry is unconfirmed: a gate that needs an artifact confirmed requires that no entry targeting it is still `proposed`. Each node's `## Format` holds the per-artifact payload shape and anchor grammar, one shape per node.
