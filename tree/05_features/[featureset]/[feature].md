# _concept/05_features/<featureset>/<feature>.md

One feature, from a sentence to a spec somebody can build. It is the one record of who may do what and of what was considered in or out; `experience-behaviors`, the seed, scaffolding, the build ledger and `mockup-storybook`'s feature page cite it, so none restates it. `spec-feature` writes it, one feature per run, and proposes the feature's roster row in the same run (`tree/05_features/featuresets.md`, whose owner `concept-brief` promotes it); the flow draws that node once because iteration is not something a flow edge can express, so the repetition lives in the skill. It lists the screens the feature uses and calls `experience-screen` for one that does not exist yet; it writes no screen itself, since a screen is `experience-screen`'s artifact.

One key is not `spec-feature`'s: `build-plan` writes `tracker:` and nothing else in this file. It records the spec's **parent issue** in the tracker `docs/agents/issue-tracker.md` names, the issue whose sub-issues are the tickets that build the feature; `build-plan` creates it once and a rerun reuses it, so a second writer would leave the spec pointing at an issue nobody builds against. `spec-feature` carries the key through untouched.

## Format

```yaml
---
priority: must-have | nice-to-have
roles: [admin, member, guest]   # or [all_users]
permissions:                    # role → allowed actions; the one record, no body table
  admin: [create, read, update, delete]
  member: [read, update]
story_refs: []                  # journey ids from stories.yaml that motivated this feature
follows: []                    # adr:<slug> references to docs/adr/: the patterns and featureset- or feature-level records this feature follows
screens:                        # screens this feature uses; one entry per screen file
  - path: 07_screens/<screen>.md
data_entities: []               # model names from 10_blueprint/datamodel/model.yaml, e.g. [User, Session]
tracker: { issue: 101 }         # written by build-plan only: the spec's parent issue number; absent until the first build-plan run
last_updated: YYYY-MM-DD
---
```

`permissions:` takes its roles from `_concept/05_features/featuresets.md`'s vocabulary and is the only place grants are written (`tree/05_features/README.md § Permissions`). Body, in order: `## Scope` — the IN / OUT / DEFER line with a one-line rationale per item; the acceptance criteria. `data_entities` is the one feature↔entity join, each name copied from the models in `_concept/10_blueprint/datamodel/model.yaml` (format: `tree/10_blueprint/datamodel/model.md`); `screens:` holds plain entries only, and with `story_refs` follows `tree/05_features/README.md § Links in both directions`. `follows:` lists, as `adr:<slug>` (`tree/docs/adr/README.md § Format`, *Referencing*), every `pattern` record the feature follows and every `featureset` or `feature` level record that shaped it (`tree/docs/adr/README.md § Levels`); a `product` record binds every feature and is not listed. `build-plan` reads it to find the shared module of each pattern.

**Proposal entry** (`tree/proposals/README.md`). `experience-screen` writes into its run's proposal file, never into this spec. The `anchor` is `screens` with the payload `{ path: 07_screens/<screen>.md }`, the entry the screen's side of the link needs, or `section:<heading>` with a markdown string to add under that `##` heading (an acceptance criterion an error state of the screen implies, under the criteria heading). A pending `screens` entry counts for the cross-link until `spec-feature` settles it (`## Writing it`, step 8).

Criteria are cited by id (`AC-<story-id>-<nn>`), never retyped; the id grammar and the table of sources to derive them from are in `tree/04_journeys/stories.md`. A criterion the grill adds that no story carries takes `AC-<feature_slug>-<nn>`.

### Slug

`feature_slug` matches `^[a-z][a-z0-9-]{1,47}$`: lowercase the title, replace each run of non-`[a-z0-9]` with one `-`, trim `-` at both ends, truncate to 48. A feature slug names three things at once — this file, its roster row and `_concept/08_dossiers/<feature_slug>/` — and resolves by globbing `05_features/*/<feature_slug>.md`. Zero matches means the spec was never written; two matches means two featuresets claim the slug, so list both and ask which one this is. A slug that already exists is a resume: load what is there, show what would change, and write after the user agrees — overwriting silently discards the reasoning a dossier holds.

## Writing it

Numbering is the run's order; steps 2, 7 and 10 hand to the nodes they name at the moment they say.

1. **Resolve the feature and its slug.** Take a one-sentence title, derive `feature_slug` as above, and place it in exactly one featureset. A glob that already resolves is a refinement of an existing spec: load it and say so before asking anything, so the user answers against what is written rather than from memory. Carry its existing `screens:` array and `tracker:` key through untouched — screens were linked by other runs and the tracker key is `build-plan`'s, and a rewritten spec that drops either silently unlinks the feature from its screens or its parent issue.
2. **Compare it with what exists, before the grill.** An `open` dossier at `_concept/08_dossiers/<feature_slug>/index.md` is an interrupted run: load it and continue where it stopped. Read the decision records that bind this feature (`tree/docs/adr/README.md § Levels`).

   Then compare the feature with every spec under `05_features/` and every row of the roster's `## Ideas` (`tree/05_features/featuresets.md § Ideas`) on what they share: entities, the actions a role takes, screens, and the floorplans of those screens. Also compare it with the `applies_when` of every `pattern` record in `docs/adr/` and in the pending proposal entries targeting it.

   Put each match to the user in one decision batch (`tree/protocol/running.md § How a skill runs`, rule 2), with three options, recommendation first:
   - **reuse** the existing feature: this run becomes a refinement of its spec (step 1's resume), and an idea that is this feature moves at step 7;
   - **generalise** the shared part into a `pattern` record (`tree/docs/adr/README.md § Patterns`) that both specs list in `follows:`; the sibling spec gains the `adr:<slug>` in this run's write set (step 9);
   - **keep it separate**, with the reason, so the next comparison does not raise it again.

   A pattern whose `applies_when` matches is followed rather than asked again; a feature that should differ from it is a contradiction (`tree/docs/adr/README.md § Levels`, rule 2). Generalise only where the shared part is used the same way: two features that merely touch one entity stay separate. Once the batch is answered, open the dossier of the feature this run specifies (`tree/08_dossiers/[feature_slug]/index.md`), the existing feature's on reuse, so no dossier is left open under a slug nobody specifies; record there every match, the option taken and the reason, or that nothing matched.
3. **Grill.** Call the Skill tool with "grilling" against this feature. If it is not installed, run the rounds yourself: one frontier of unsettled questions per message, each with a recommended answer. The ground the frontier has to cover before it can be empty: what the feature *is* and who triggers it, the happy path, state transitions, boundary inputs, concurrency, a role × action permissions table, persistence and recovery, error states, and the other features this one touches. `depth` in `_concept/01_meta/scope.yaml` (format: `tree/01_meta/scope.md`) sets the depth — `sketch` settles the happy path and permissions in a round or two; `standard` and `exhaustive` work the tree until the frontier is genuinely empty. Absent, `depth` is a question in the first batch, written into the run's proposal file per `tree/01_meta/scope.md § Asking a missing key`. Resolve facts before asking (`tree/protocol/running.md § How a skill runs`, rule 1): read `_concept/brief.md`, `_concept/04_journeys/stories.yaml`, `_concept/06_behaviors/<featureset>.md` where it exists, and any sibling spec the feature touches first, and where the feature already lives in the code and the findings do not hold it, run `concept-reverse` scoped to its `routes`, `screens` and `datamodel` paths. `grilling` makes finding facts your job, and asking the user something the tree already says spends the round you needed for a real question. With no journeys, brief or data model the interview carries those loads, so ask where the feature sits in a journey rather than assuming it stands alone. Append to the dossier as its node says (`tree/08_dossiers/[feature_slug]/index.md`).
4. **Use the glossary's words; pin decisions as they pass the gate.** Name every concept in the grill by its term in the glossary (`tree/glossary.md § Where the words live`) — a synonym from the `_Avoid_` list is renamed to the term, not adopted. Entity names are read, never coined: from `_concept/10_blueprint/datamodel/model.yaml` when it exists, else from the glossary. A concept with no term is written into the run's proposal file per `tree/glossary.md § Format`, *Proposal entry*, and the interview carries on with it; `concept-glossary` settles it. A choice that passes the three-test gate is written into the run's proposal file as a decision record (`tree/docs/adr/README.md § Writing it`, target `docs/adr/`, anchor `adr:<slug>`) while the interview is running, because the reasoning is in the room only then.
5. **Draw the scope line.** Walk every edge case and open question the grill surfaced and put each one IN, OUT or DEFER with a one-line rationale. IN items become acceptance criteria; the whole line becomes the spec's `## Scope` section, the one record of what was considered, and the dossier links to it rather than copying it. A DEFER names the feature that will pick it up, or it is an OUT wearing a friendlier word. A DEFER that names a feature with no spec, no idea row and no pending entry becomes a `move: idea` entry in the run's proposal file (`tree/05_features/featuresets.md § Format`, *Proposal entry*). An OUT that clears the three-test gate is proposed as a decision record with `status: rejected` the same way, because a refusal that binds the whole design stays invisible to the next feature unless it is logged where that feature reads.
6. **Write the feature spec** at `05_features/<featureset>/<feature_slug>.md` in the format above. Cite criteria from `stories.yaml` by id; one the feature needs that its journeys lack takes `AC-<feature_slug>-<nn>`, and step 9 names the journeys' owner. Set `data_entities` from `model.yaml`; an entity the model lacks is written into the run's proposal file (`tree/10_blueprint/datamodel/model.md § Format`, *Proposal entry*) and named here, and with no `model.yaml` the list stays empty and entities are named by glossary term. Set `follows:` from step 2 and from the records the grill applied. Every criterion traces to something the user confirmed in the grill — an invented one reads exactly like a real one to the implementer, and gets built.
7. **Propose the roster row**, per `tree/05_features/featuresets.md § Writing it`: a `move: table` entry in the run's proposal file with the priority the grill's first batch settled, a new featureset's `purpose` when none fits, and a `role:` entry for any role the grill named that the roster lacks. `concept-brief` promotes them without asking the user again, because the approval in step 9 covers them.
8. **List the screens the feature uses.** First settle the pending entries targeting this spec per `tree/proposals/README.md § Writing it`: a `screens` entry whose screen file exists and names this feature in `implements:` is promoted to a plain `screens:` entry, a `section:` entry is put to the user in the step 9 batch, and each gets `status`, `settled_by: spec-feature` and `settled_on` (a rejection with its reason). Then, for each screen the scope line put IN that already exists at `07_screens/<screen>.md`, add it to `screens:` and write an entry with anchor `implements` and the payload `05_features/<featureset>/<feature_slug>.md` into the run's proposal file (`tree/07_screens/[screen].md § Format`), so the link holds in both directions (`tree/05_features/README.md § Links in both directions`) while the screen stays its owner's artifact. For each screen that does not exist yet, Call the Skill tool with "experience-screen", naming the screen and this feature's path: it writes the screen with this feature in its `implements:` and proposes the `screens` entry, which this step promotes once the screen file exists. When the skill is not installed, name the screen for the user to create and leave it out of `screens:` until it exists, so no entry points at a missing file. This skill's write set carries no screen file.
9. **Show the whole write set and the blast radius, then write.** An existing file gets its diff shown and its own answer — the user's earlier edits are the case this catches; a sibling spec that gained a `follows:` id in step 2 is shown as its own diff. Beside the diffs, name which already-written artifacts this feature just invalidated and whose owner has to re-run: `04_journeys/stories.yaml` when it introduces a flow no story covers, `10_blueprint/techstack.md` for a new dependency, `architecture.md` for a new module or protocol, `10_blueprint/datamodel/` for new entities or fields, and `07_screens/shell.md` when it adds a top-level destination, and `experience-screen` for a screen the feature changes. Naming the owner is the whole of it — this skill edits none of them, and a cascade that reaches into five trees is the tangle of several owners per artifact that one owner per artifact exists to avoid. The feature is specified, not planned: `build-plan` owns the plan.
10. **Freeze the feature dossier**, per `tree/08_dossiers/[feature_slug]/index.md`.

## Checks

- The spec, its roster row or its pending `move: table` entry, and the frozen dossier are on disk.
- Every `screens:` entry names a screen file that exists and whose `implements:` names this feature, or a pending `implements` entry for it does.
- No pending proposal entry targets this spec after a run that had the user in the room, except one the user deferred.
- `permissions:` is the only place grants appear.
- Every acceptance criterion is an id traced to the user's confirmation in the grill; every IN item has one.
- Every `follows:` entry is an `adr:<slug>` that resolves to a record in `docs/adr/` neither `rejected` nor superseded, or to a pending proposal entry (`tree/docs/adr/README.md § Format`, *Referencing*).
- The dossier records the similarity check: each match with its option and reason, or that nothing matched.
